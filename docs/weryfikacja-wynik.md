* **MCP Silicon Labs:** DOSTĘPNY. Serwer `silabs-knowledge-base` (semantyczne wyszukiwanie w kodzie/dokumentacji/komponentach SDK 2026.6.1). Próbne zapytanie o **EFR32MG24B220F1536IM48** zwróciło z nagłówka SDK `efr32mg24b220f1536im48.h`: `FLASH_SIZE = 0x00180000` (1536 KB), `SRAM_SIZE = 0x00040000` (256 KB), `FLASH_PAGE_SIZE = 0x2000` (8 KB).   * Twierdzenia na poziomie **płytki Seeed XIAO MG24** (obecność/brak baterii RTC, mostek SAMD11/CMSIS-DAP) nie są w bazie Silicon Labs — nie audytowano ich wobec MCP.
  * **Nie** audytowano linia-po-linii dużych plików `refactorings/README.md` (1767 linii) ani `todo.md`; pominięto też `security_evaluation_prompt.md` i `weryfikacja_prompt_magnum.md` (materiał pomocniczy, zgodnie z zakresem).
  * Nie uruchamiano firmware na sprzęcie; weryfikacja behawioralna opiera się na odczycie kodu źródłowego.

**Uwaga metodyczna:** audyt skupia się na twierdzeniach **sprawdzalnych w kodzie lub w MCP**. Krótsza tabela realnych rozbieżności przedłożona nad długą listę domysłów. Twierdzenia potwierdzone jako poprawne są w sekcji 3.

## 4. „NIE DO ZWERYFIKOWANIA” / niezależnie niepotwierdzone (istotne dla bezpieczeństwa)

* **PSA Certified Level 3, maskowanie DPA, TRNG NIST SP 800-90A/B/C** (`compass_security_mechanisms.md:13,23,66-72`) — to publiczne, prawdopodobnie poprawne cechy Secure Vault High w EFR32MG24, ale **nie** potwierdzono ich niezależnie przez MCP w tej sesji (wyszukiwarka SDK nie zwraca certyfikatu PSA). Brak dowodu ≠ dowód błędu.
* **Dokładna numeracja i semantyka sygnałów tamper SE** (17 EMPGD, 18 SUPGD, 21 BOD, 22 temperatura, 23/24 DPLL, 25-31 PRS) — spójna między `antitamper.md` a komentarzem `tamper_manager.c:133-135`, ale **nie** potwierdzona wprost z `sl_se_manager_defines.h` przez MCP (wynik przekraczał limit odpowiedzi). Przyjęto jako spójne wewnętrznie.
* **Pełna zgodność bajtowa handshake/AAD/licznika między PC (`secure_channel.py`/`protocol.py`) a MCU (`session_ecdhe.c`/`router_common.c`)** — opis dokumentów jest spójny, ale nie wykonano porównania implementacja-vs-implementacja (poza odczytem stałych). Do pełnego audytu kryptografii potrzebny osobny przebieg.
* **Zachowanie na sprzęcie** (device erase, przetrwanie logu, odblokowanie SWD po LOCK, wykrycie tamper w EM2) — dokumenty same oznaczają te punkty jako „niezweryfikowane na sprzęcie”; audyt kodu to potwierdza, ale testu sprzętowego nie wykonano.

## 5. Ustalenia i zmiany — tamper / OTP (2026-11-12)

Szczegóły: [antitamper.md](security/antitamper.md) — master table + sekcja „Plan warstwy OTP / Secure Engine".

**Wdrożone (software, odwracalne, `tamper_manager.c:34-45`):**
* Progi VRX 30/30/50/30 → **50/50/50/50** (tolerancja pod roczne sesje; token 32-bit — liczba nieistotna kryptograficznie).
* Temperatura próg 3 → **12** (≈60 s poza −10/+70; awaria klimy w serwerowni nie kasuje klienta).
* Voltage (BOD) i Digital (HFXO) → **tylko log, nie wipe** (wpięcie USB / słaby start kwarcu fałszywie je wzbudzają; realny glitch łapie SE 17/18).
* Obudowa pozostaje **1**.

**Do zaprogramowania (warstwa SE / OTP — NIEODWRACALNA, tylko w provisioningu produkcyjnym `--lock`):**
* SE 17 (EMPGD) i 18 (SUPGD) → **poziom OTP 4 (reset)**, nie wipe i **nie brick**: fałszywie wzbudzają się (ESD, brudne USB, inrush, EM). Reset jest niedestrukcyjny i logowany (`SE_TAMPER_RESET`). Po **50 resetach-tamper** (lifetime, NVM3) firmware robi odwracalny wipe na czystym starcie.
* SE 10/11 (brute-force unlock) → poziom 1, wipe po 10. SE 15 (TRNG) → poziom 1, tylko log. SE 22 (temp) / 23–24 (DPLL) → pomijamy. PRS (25–31) → pominięte (Secure Debug Lock zamyka ten wektor).
* **erase OTP (poziom 7) — nigdy.** `sl_se_init_otp` zamraża też decyzję o secure boot; wykonywane wyłącznie w `provision_dongle --lock`.

**Potwierdzenia z kodu/SDK (ta sesja):** `SE_TAMPER_RESET` logowany na reboocie `tamper_manager.c:150-153`; numeracja sygnałów SE dla MG24 (S2C4) z `sl_se_manager_defines.h` (17 EMPGD, 18 SUPGD, 21 BOD, 22 temp; 0/3/6/13 = RESERVED); `sl_se_erase_device` zostawia stronę User Data i OTP.
