* **Data audytu:** 2026-11-13
* **Audytowane repozytoria i wersje (snapshot w chwili audytu):**
  * **Compass** — gałąź `make-it-same`, HEAD `efa3aeaa` (*feat(app): add timing and setup hooks*)
  * **KeySec** — gałąź `main`, HEAD `778e910` (*docs(security): document production hardening*) — dokumentacja audytowana w tym commicie
  * **KeyFirmware** — gałąź `main`, HEAD `6280047` (*feat(tamper): add SE OTP arming*)
* **MCP Silicon Labs:** **DOSTĘPNY i odpowiadał.** Próba kontrolna dla `EFR32MG24B220F1536IM48` zwróciła z nagłówka SDK `FLASH_SIZE 0x00180000` (**1536 KB**) i `SRAM_SIZE 0x00040000` (**256 KB**); tier części „B2xx" = **Secure Vault High**. Baza MCP (Kapa) pokrywa reference manual / nagłówki SDK EFR32xG24 oraz komponenty `sl_se_manager`; **nie** pokrywa cech płytki Seeed XIAO MG24 (mapowanie modułu, mostek SAMD11, bateria) — te oznaczono jako board-level.
* **Zakres:** 23 pliki `.md` z `KeySec/docs/` (poza `refactorings/`, `security_evaluation_prompt.md`, `weryfikacja-prompt.md`, `weryfikacja-wynik.md`). Każdy plik przejrzany wiersz-po-wierszu przez wyspecjalizowany tor audytu, a każde znalezisko zostało **niezależnie zweryfikowane przez orkiestratora** względem cytowanej linii kodu przed wpisaniem do tabeli.
* **Dostępy:** pełny odczyt trzech repozytoriów + MCP Silicon Labs. Nie zabrakło żadnego wymaganego dostępu. Elementy board-level i pomiarowe (prądy mA/µA) są z natury poza MCP i kodem — ujęte w sekcji „NIE DO ZWERYFIKOWANIA".

## 2. Podsumowanie

22 potwierdzone/prawdopodobne rozbieżności: **0 KRYTYCZNYCH**, **4 WYSOKIE**, **10 ŚREDNICH**, **6 NISKICH**, **2 INFO/LUKA**.

**Wniosek nadrzędny:** rdzeń bezpieczeństwa jest opisany **wiernie**. Wszystkie twierdzenia o algorytmach kryptograficznych (ECDHE P-256, HKDF-SHA256, podwójne klucze AES-256-GCM, format nonce, anti-replay), o kluczach (klucz tożsamości ECDSA P-256 owinięty PUF `0x81001`, certyfikat = podpis Root CA, klucz logu AES-128), o anti-tamperze (poziomy SE, progi, brak auto-brickingu) oraz o gwarancjach „nie do obejścia" zostały **potwierdzone 1:1 w kodzie i/lub MCP**. Nie znaleziono błędu, który przy wdrożeniu wg dokumentu łamałby bezpieczeństwo — stąd brak pozycji KRYTYCZNYCH.

Rozbieżności koncentrują się w: (a) opisie **uwierzytelniania** aplikacji hosta (udokumentowany Keycloak SSO nie istnieje — faktyczny login jest lokalny), (b) **parametrach sprzętowych** w `battery_sleep.md` (zegar rdzenia, zbocze wybudzenia), (c) **warstwie ochrony aplikacji** (nieistniejąca „Nuitka VM", zawyżona gwarancja o zrzucie pamięci) oraz (d) **nieistniejących plikach/ścieżkach** w dokumentach architektury i migracji (`compass_rpc.py`, `rpc_router.c`, `src/logic/`, `read_all`).

> **Kontekst dla `cryptography_flow_and_keys.md`:** plik jest jawnie **starszym dokumentem projektowym**, który `klucze_i_provisioning.md` §8 celowo zastępuje. Jego rozbieżności (pozycje #5, #15, #21, #22) to „dokument opisuje starszy/planowany projekt", a nie błędy aktywnego kodu — zaznaczono to w opisach.

## 4. Twierdzenia sprawdzone i POTWIERDZONE jako poprawne (skrót)

Poniższe kluczowe mechanizmy zostały zweryfikowane w kodzie/MCP i **są zgodne** z dokumentacją (lista zdawkowa — żeby autor wiedział, że zostały przejrzane, nie pominięte):

* **Kanał szyfrowany:** ECDHE **P-256**; HKDF-SHA256 (salt = `pc_nonce` 32 B); **dwa** klucze AES-256-GCM (`client/server_write_key`); nonce 12 B (licznik LE + bajt kierunku `0x01/0x02` + 7 zer); AAD żądanie `[cmd_id]`, odpowiedź `[cmd_id, OK/ERR]`; anti-replay „strictly greater"; timeout bezczynności sesji 300 s. *(`secure_channel.py`, `session_ecdhe.c`, `core_messages.h`, `constants.py`)*
* **Klucze i tożsamość:** klucz tożsamości **ECDSA P-256** owinięty PUF (`SL_PSA_KEY_LOCATION_WRAPPED`, `IDENTITY_KEY_ID = 0x81001`); certyfikat = podpis Root CA nad kluczem tożsamości (65 B / ≤72 B); Root CA pub wczytywany z pliku; klucz logu tamperów **AES-128-ECB**, celowo nie owinięty PUF; klucze fabryczne (Root CA / Host / Command = ECDSA P-256). *(`auth_manager.c/.h`, `keyadmin/scripts/generate_*.py`)*
* **Anti-tamper / Secure Debug:** poziomy reakcji SE 0/1/2/4/7 (MCP); poziom 7 (erase-OTP, trwały brick) **nigdy nie używany**; `tamper_reset_threshold = 0` (brak auto-brickingu); progi PIN1/PIN2 = 1, VRX ×4 = 50, TEMP = 12 (×5 s), VOLTAGE/DIGITAL = log-only; Secure Debug Lock = 3 kroki (`init_otp_key` → `enable_secure_debug` → `apply_debug_lock`); token unlock 220 B; device-erase zostawia układ odblokowany (MCP); User Data `0x0FE00000`, 1 KB, przetrwa device-erase (MCP). *(`tamper_manager.c`, `sec_tamper_otp.c`, `sec_debug_lock.c`)*
* **Sprzęt (MCP):** EFR32MG24 **Secure Vault High**, Flash **1536 KB** / RAM **256 KB**; Cortex-M33 Armv8-M TrustZone; SYSRTC na LFRCO 32768 Hz, działa w EM2; EUSART FIFO 16 B; numeracja sygnałów SE (EMPGD 17, SUPGD 18, BOD 21, TEMP 22); „brak domeny RTC z baterią" poprawne dla xG24 (BURTC obecny, lecz nieużywany).
* **Mapa pamięci / protokół:** podział Secure/NSC/NS Flash i NVM3 zgodny z `linkerfile_s.ld/ns.ld`; TinyFrame **CRC32** po obu stronach; EUSART 921600; opcody RPC (`0x01-0x16`, `0x60-0x65`) zgodne z nagłówkami routerów.
* **Build hosta:** `--mode=standalone` (NIE `--onefile`); 3 autorskie DLL force-bundled; flagi Themida/Nuitka opisane jako włączone/wyłączone zgadzają się z `build-nuitka-comm-themida.ps1`.
* **Login / sesja (host):** tożsamość = `CRC32("<email>|<device>")`; jeden token na login + unieważnianie; strażnik sesji co 3 s; `BrowserProbe`/`clean_device`; RTC checkpoint 60 s + kara 150 s (próg NO_RTC 210 s), reset tylko „do przodu", `RTC_MIN_VALID_TIME = 2024-01-01`.

## 5. NIE DO ZWERYFIKOWANIA (z powodem)

* **Typ PUF = „SRAM PUF"** (`cryptography_flow_and_keys.md:13`) — MCP zwracał tylko nagłówki rejestrów, bez dokumentacji Secure Vault PUF. Mechanizm wrapped-keys potwierdzony kodem (`SL_PSA_KEY_LOCATION_WRAPPED`), ale sam szczegół „SRAM" niepotwierdzony vs źródło sprzętowe. Brak kontr-dowodu → nie zgłoszono jako błąd.
* **Twierdzenia board-level Seeed XIAO MG24** — mostek SAMD11/DAPLink CMSIS-DAP, reset-do-bootloadera, bateria LiPo Akyga, mapowanie pinów modułu, kwarc LFXO PD00/PD01, „brak dedykowanej baterii domeny RTC" (`hardware_and_environment.md`, `battery_sleep.md`, `antitamper-casing-debate.md`). Poza bazą Silicon Labs; spójne wewnętrznie i z komentarzami firmware.
* **Wartości prądów** ~6-8 mA (EM0), ~1,5-2,5 mA (EM1), ~2-3 µA / ~1 µA (EM2/3) (`battery_sleep.md:18-20`) — pomiarowe; dokument sam hedżuje; nieweryfikowalne z kodu/MCP.
* **Lądowanie EM2 vs EM3** (`battery_sleep.md`) — dokument jawnie hedżuje „EM2/3"; `sl_power_manager` schodzi do EM2, logi mówią „EM3". Genuinna niejednoznaczność.
* **Progi czujnika temperatury SE** „~−35/+120 °C" (`antitamper.md:184,231`) — brak konkretnej wartości progowej w MCP; dokument hedżuje „~" i „celowo" — nie przeszacowana gwarancja.
* **Logowanie cofnięcia zegara** (`time_license_mechanism.md:26`) — `security_rtc_set_time` (obraz fabryczny) nie loguje cofnięcia; ewentualny log może być w routerze admina (nieczytany). Brak kontr-dowodu → niepotwierdzone, nie zgłoszone jako błąd.
* **Konfiguracja anti-debugger Themidy** (`app_protection_nuitka_themida.md:21`) oraz ogólne zachowanie narzędzi 3rd-party (Nuitka, Themida Anti-Dump) — zależne od projektu `.tmd` / poza repo; PRAWDOPODOBNE, nie błąd. *(Pominięcie anti-debuggera Nuitki jest osobno potwierdzone.)*
* **Historyczna lokalizacja Secure NVM3** `0x08174000` (§2.6 `compass_security_mechanisms.md`) — oznaczona w dok. jako historyczna; bieżący Secure NVM3 jest na `0x08026000` (potwierdzony w linkerach).
